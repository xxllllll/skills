# Release Notes 规则全文

## 1. 先适配目标项目，再套默认约定

在已有仓库撰写或改写 Release Notes 之前，先确认三件事：

1. 仓库是否存在 `AGENTS.md`、`CHANGELOG.md`（例如 Keep a Changelog 流程）或发布脚本；若有，尊重其章节存储位置与发布入口，将本规范用于**正文质量、分层与措辞**。
2. 查看最近 2–3 条已发布的 Release，了解项目受众（个人自用 / 内部运维 / 公开开源）、常用区域术语与安装方式。
3. 运行 `scripts/collect-changes` 拿到真实的提交区间与 diff 规模，再动笔。

原则：**面向使用者的公告质量优先于机械拼 log**；项目已有的领域名词和发布入口优先于默认值。

---

## 2. 素材采集与事实核验

Release Notes 最大的失信来源是「凭 commit 标题猜细节」。起草时遵守：

1. **以区间提交 + diff 为唯一事实来源**：
   - 运行 `scripts/collect-changes [repo] [--from TAG] [--to REF]` 获取上一版 tag 到目标 ref 之间的非 merge 提交。
   - 若仓库是首次发布（尚无历史 tag），覆盖范围默认为初始提交到 `HEAD`，直接写首版核心能力与部署方式，不逐条罗列建仓过程。
2. **模糊标题必须回查**：
   - 看到类似「优化体验」「收口状态机」「重构协议层」的标题，必须查看对应 commit 正文（`--full` 或 `git show --stat <sha>`）确认**用户到底感受到了什么变化**。
   - 核验不到的性能数字、平台支持、兼容性承诺一律不写；宁可写实（如「降低后台空闲内存占用」），绝不编造百分比。
3. **版本标签兼容**：
   - 支持标准 SemVer（`v1.2.3`）、预发布（`v0.26.0-rc.1`）以及带构建号标签（`v0.2.161+167`）。
   - 预发布版（`rc` / `beta` / `alpha`）在首段明确标出「本次预览版 / 候选版」，并在安装提示中标注预览渠道或回退方式。

## 3. 噪音过滤与例外提回

发布说明只记录**使用者或部署者关心**的变化。过滤按 `type` 和 `scope` 双重判断：

### 默认不进正文

- **按 `type`**：`chore`、`ci`、`test`、`docs`、`style`、`refactor`、`build`。
- **按 `scope`**（即使提交标了 `feat` 或 `fix`）：
  `release`、`scripts`、`tests`、`test`、`ci`、`docs`、`doc`、`adr`、`agents`、`skills`、`lint`、`tooling`、`dev`、`bench`。
- **固定忽略**：版本号推进提交（`chore(release):`）、合并提交、回滚后又重做且净改动抵消的中间提交、记账/归档提交。

### 必须人工提回的 4 种例外

采集脚本会把过滤掉的提交保留在「内部提交摘要」里供快速扫一眼。遇到以下情况必须人工提回正文：

1. **安全修复**：哪怕归在 `deps` 或 `build`（如升级某库修复 CVE / RUSTSEC），必须进入正文，必要时单列 `## 🔒 安全` 或置顶升级提示。
2. **破坏性变更或迁移要求**：任何带 `!:`、`BREAKING CHANGE:`，或改变了环境变量、配置文件格式、最低支持系统/客户端版本（如 `minBuild` 强制更新）的提交。
3. **可感知的底层重构或依赖升级**：虽标为 `refactor`/`build`，但显著降低了安装包体积、内存占用、启动耗时，或新增了发行架构/安装包（如新增 Linux ARM64 独立包）。
4. **文档型重要变更**：仅当发布了新的关键部署方式或下线旧部署方式时提及，常规 README 排版与 ADR 永远不进 Release Notes。

## 4. 翻译原则：开发语言 → 用户语言

| 维度 | 开发视角（不要直接照搬） | 用户视角（应该这样写） |
| --- | --- | --- |
| 前缀与编号 | `fix(emby-reporting): 按配置轮询周期调度当日对账 (67ed3034)` | `播放报告：按配置的轮询周期调度当日对账，避免重复或漏跑` |
| 内部实现 | `perf(index): 短路无实质变更的子树传播枚举` | `索引扫描：无实际改动的目录跳过重复扫描，减少无效磁盘与 CPU 开销` |
| 内部术语 | `refactor(organize): 清退废表、死列与 ADR-0014 历史豁免` | 若无外部影响则直接过滤；若涉及旧接口/配置移除则写入升级提示 |
| 多条同源修补 | 拆成 5 条细碎的小修 | 合并为 1 条主题描述，如「远端文件预览：修复 HTML、图片、PDF 与 Office 预览报错」 |

### 书写约束

- **列表句式统一**：`- 场景/模块：用户可感知的变化`（有对应公开 PR/Issue 时在句末附 `(#123)`）。
- **禁止泄露到正文的内容**：
  - 原始 `type(scope):` 前缀；
  - 裸 commit SHA（如 `` (`e6d69988`) ``）；
  - 仅项目内部有意义的文档编号（如 `ADR-0014`）、内部表名/函数名/测试夹具名（除非面向 SDK/CLI 开发者且属于公开 API）。
- **长尾折叠**：当某一分组（通常是 `## 🐛 修复`）超过 12 条，或存在大量边角稳定性微调时，优先合并同模块项，并将不值得单独展开的零碎条目收束为末行 `- 另有 N 项稳定性与细节修复`。

## 5. 两档结构模板

### 档位 A：精简版（补丁 / 小版本）

适用条件：用户可见变更 ≤ 4 条，且集中在单一或两个紧邻主题。**不写 `###` 亮点段**，避免同一件事重复说两遍。

```markdown
本次更新修复了取流协议异常回退问题，并收窄热修熔断触发条件，提升播放稳定性。

> ⚠️ **升级提示**（仅存在破坏性变更、迁移或升级坑时保留，否则整块省略）

## 🚀 新功能
- 播放解析：强化取流协议容错，上游字段微调时自动回退可用线路

## 🐛 修复
- 规则热修：收窄熔断触发条件，热修异常时自动回滚至已验证版本

## 安装与升级（按需保留）
- 从下方 Assets 下载对应平台安装包，或按项目常用方式更新。
```

### 档位 B：标准版（功能版 / 多场景聚合大版本）

适用条件：用户可见变更 ≥ 5 条，或横跨 ≥ 2 个用户关心的业务场景。采用「总览 → 风险提示 → 场景亮点 → 分组明细 → 安装指引」的倒金字塔结构：

```markdown
本次更新带来多端同步、自定义导出与冷启动加速，并修复了若干播放与并发配置保存问题。

> ⚠️ **升级提示**：本次移除了旧版配置文件中的 `[legacy.mounts]` 字段，升级前请先运行迁移脚本；详见下文安装说明。

### 🌐 场景主题一（把同场景的新功能 + 修复 + 优化合写成一段）
用 2–3 句连贯人话讲清这组变化给使用者带来了什么实际体验提升，避免堆砌实现细节。

### ⚡ 场景主题二
把相关的性能优化、内存降低或稳定性改进聚在一起，有实测数据时写清前后对比。

## 🚀 新功能
- 场景/模块：清晰说明新增了什么能力、怎么用（可选 `(#PR)`）

## ⚡ 性能与优化
- 场景/模块：说明快了/省了什么以及对应场景

## 🐛 修复
- 场景/模块：说明原先什么现象、现在恢复成什么表现（可选 `(#PR)`）
- 另有 N 项稳定性与细节修复

## 安装与升级（按需保留）
- 安装 / 升级命令
- 平台常见避坑（例如 macOS 提示无法验证应用时的 `xattr` 命令、Docker 镜像拉取命令）
- 校验和与更多文档链接
```

### 分组标题约定

按需出现，**空分组不渲染**：

- `## 🚀 新功能`（对应英文 `## 🚀 Features`）
- `## ⚡ 性能与优化`（对应英文 `## ⚡ Improvements`；数量少时可并入新功能或修复）
- `## 🐛 修复`（对应英文 `## 🐛 Fixes`）
- `## 🔒 安全`（对应英文 `## 🔒 Security`；仅含安全修复时出现）
- `## 安装与升级`（双语时共用 `## Install & Upgrade`）

亮点段 `###` 建议控制在 **2–6 组**，每组配一个表意清晰的单一 emoji（如 `🛡️` `🌐` `⚡` `🖥️` `📱` `🤖` `✍️` `🧩`），避免无意义装饰堆砌。

## 6. 升级提示与破坏性变更写法

满足以下任一条件时，**必须**在首段总览之后、亮点之前放置 `> ⚠️ **升级提示**` 引用块：

- 存在 `BREAKING CHANGE`（删除旧接口、旧配置键、旧运行平台或旧数据表）；
- 需要人工执行迁移脚本、重建索引或重启特定服务；
- 存在强制最低版本门槛（如 `minBuild` 升级闸门）；
- 存在已知的跨版本升级坑（如镜像同步延迟、旧版更新器无法直接覆盖）。

每条升级提示说清三件事：

1. **影响谁**：哪类部署方式、旧版本或旧配置受影响；
2. **怎么处理**：给出可直接复制执行的命令或操作步骤；
3. **边界/收口**：是否一次性操作、从本版起是否已修复不再需要。

## 7. 可选开关（按项目类型启用）

| 选项 | 默认值 | 何时开启 | 格式要求 |
| --- | --- | --- | --- |
| 中英双语 | 关闭（纯中文） | 公开开源且有海外用户 | 完整中文在前 → 独立一行 `---` → 完整英文在后；文末 `## Install & Upgrade` 与 `## 🙏 致谢 / Thanks` 只写一次共用 |
| 署名与致谢 | 关闭 | 多人协作开源仓库 | 每个 `###` 亮点段末新起一行写 `— @user1 · @user2`；文末加 `## 🙏 致谢 / Thanks` 按贡献者聚合 PR 号 |
| 产物与校验和 | 按需 | 多端安装包 / 二进制 / 插件 | 在 `## 安装与升级` 写明各平台包名对应关系，或附 MD5/SHA256 校验说明 |

英文版不是机翻直译：遵循同样的倒金字塔与用户视角，保持专有名词、命令、PR 号与中文版一一对应。

## 8. 发布落地与渠道防坑

1. **优先文件传参**：
   ```sh
   gh release create v1.2.0 --verify-tag --title "项目名 v1.2.0" --notes-file release-notes.md
   # 补写或润色已有 Release
   gh release edit v1.2.0 --notes-file release-notes.md
   ```
2. **不要裸用 `--generate-notes`**：无 PR 流程或未配 `.github/release.yml` 时，GitHub 会只输出一行 `Full Changelog` 对比链接。
3. **`git tag -a` 承载 Markdown 必须防吃标题**：
   - Git 默认使用 `cleanup=strip`，会把 `-m` 中所有 `#` 开头的行当注释删除，导致 `# 标题` 和 `## 分组` 全部蒸发。
   - 若项目通过 annotated tag 保存 Release Notes，创建标签时必须显式加上 `--cleanup=verbatim`（或从文件读取并加 `--cleanup=verbatim`）：
     ```sh
     git tag -a v1.2.0 --cleanup=verbatim -F release-notes.md
     ```
4. **发版前质检**：把终稿喂给 `scripts/check-release release-notes.md` 确认零错误，再推送发布。
